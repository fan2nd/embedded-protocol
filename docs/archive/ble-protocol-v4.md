# 串口 BLE 可靠传输协议 v4（滑动窗口）

本文保留 v4 历史定义。当前实现见 [BLE v6](../ble-protocol.md)，历史结果不能当作当前版本结果。

本版约定只保留 HELLO、DATA、ACK，逐包累计确认，固定容量滑动窗口。当时通用编解码、会话状态和滑动窗口位于 `crates/ble-link-protocol`（该 crate 现已升级 v6），测速命令和统计属于应用载荷。



## 帧与类型

```text
A5 5A | type:u8 | session:u128 | id:u32 | length:u16 | payload | CRC32C:u32 | 5A A5
```

整数小端，固定开销 31 字节，载荷最多 1024 字节。CRC32C 覆盖包头至载荷末尾。按长度定位包尾，通过 CRC 后处理；校验错误逐字节重新寻找包头，字节间空闲达到 1 秒清除残帧。只约束包头包尾以避开 AT、+++、CR/LF，帧体不转义；AT 配置与透传阶段分离。

| 类型 | 值 | 用途及 id 含义 |
| --- | --- | --- |
| HELLO | 1 | 建立会话，握手阶段不占数据 ID |
| DATA | 2 | 应用数据；每个方向独立从 0 递增，重传保留 ID 和内容 |
| ACK | 3 | id 为本方向接收端的下一期待 DATA ID；空闲时同一格式用作心跳 |

ACK 不分配新的数据 ID，也不需要 POLL 或独立轮次号。ACK(next=N) 表示本会话中对方发送的 DATA ID 小于 N 的连续前缀已经接收。DATA ID 不回绕，耗尽前建立新会话。测速开始、结束和统计不增加链路包类型。

## 逐包确认与固定滑动窗口

- 每接收一个通过校验且可交付的按序 DATA，推进接收位置，并立即调度 ACK；不等窗口收满，也不等待发送端查询。重复包不重复交付，仍回复当前 ACK；乱序包丢弃并回复当前 ACK，不跨越缺口确认。
- 接收应用没有容量时，不交付也不推进确认。调用方必须先确保有界接收队列可容纳数据，再调用接收状态机推进位置。
- 启动即使用配置窗口，范围 1..8 包，同时限制未确认整包字节总量（64..8192）。不慢启动、不增窗、不缩窗。
- 收到合法 ACK 后立即释放已确认包及其字节额度；只要包数和字节额度允许，立即补发新 DATA，**不等待整个窗口确认**。
- 例：窗口为 4，已发送 ID 0、1、2、3。收到 ACK(next=1) 就释放 ID 0 并可发送 ID 4，此时 ID 1、2、3 仍未确认；收到 ACK(next=3) 再释放 ID 1、2，并可发送 ID 5、6。
- ACK 必须匹配活动 session，且满足 `base < next <= 已开始发送的下一数据 ID`。重复、回退、超范围和旧会话 ACK 不推进窗口，不触发额外重传，不延长任何包的超时。
- 一个接收块中的 ACK 全部处理。每次新提交或重传前重新检查确认位置，已确认包不得再次启动发送。Mac 每个 ATT 分片及等待写队列期间也检查 ACK，已确认的重传副本可以停止后续分片；已提交字节无法收回，残帧按 CRC、包头重同步和空闲超时恢复。

## 独立重传与半双工调度

每个未确认 DATA 独立保存最后提交时间和发送次数。初发完成后等待 100 ms，第一次重传后等待 200 ms，之后每次等待 400 ms；最多 8 次发送（初发加 7 次重传）。时间从该包提交完成计起：UART 为 flush 完成，Mac 为本地 BLE 栈提交完成，均不表示对端已收到。

超时只使对应的未确认包具备重传资格，不整窗重发，不重置其他包计时器。ACK 推进后，剩余包保留原有截止时间。重传前再次检查确认状态，重复 ACK 不触发快速重传。达到发送上限则报告失败，不能假装完成，也不能通过缩窗或重置 ID 继续同一数据流。

UART 一次突发是一个完整协议包，不将窗口合并成大突发，不人为拆成固定小块加延时。帧间优先处理接收和待发 ACK，再调度到期重传及新数据；半双工发送中只能在当前完整 UART 包结束后发送 ACK，不要求中断已经提交的包。ACK 不占 DATA 窗口额度，必须保留控制帧发送空间，避免窗口满后双方无法发送确认。待发累计 ACK 可以保留最新接收位置，不为每个旧位置建立无界队列。

本地队列可写或 UART flush 不能证明模块内部有空闲缓冲。窗口仅限制在途包和字节，不能替代模块 RTS/CTS 或模块级确认。没有这些反馈时保留丢包、重复和重传统计，不能宣称零丢包或已经测到信道绝对极限。

发送方保留全部未确认包的原始内容，确认后释放；只有可按 ID 精确重建的测试数据允许重新生成。接收方仅按序交付，不为乱序包增加额外缓存。ACK 心跳携带当前接收位置，不对 ACK 再发送 ACK；心跳不推进 DATA ID，也不重置未确认数据包的超时。链路空闲检测时长由双方应用配置，与 100/200/400 ms 重传时序分开。

## 会话与抗重放

HELLO 完成客户端随机数、设备新随机挑战及确认的交换，各阶段共用 HELLO 类型。待确认握手不能清除活动会话；重复确认不能重置数据 ID。仅确认匹配待确认挑战时切换新会话。请求 HELLO(session=0,id=0) 载荷为 `RLB4 + client:u128 + byte_budget:u32`；挑战 HELLO(session=新挑战,id=1) 回显 client；确认 HELLO(session=新挑战,id=2) 携带 client。设备回复能力 ACK，id 为当前接收位置，载荷为 baud:u32、max_payload:u16、max_packets:u16、version:u16（4）、max_window:u16、byte_budget:u32。

设备以硬件随机源生成 128 位会话挑战。旧会话 DATA、ACK、确认不能改变当前交付状态；已交付 DATA 不重复交付。会话过滤先于窗口处理，滑动窗口状态机本身不接收或验证 session，调用方负责检查。

该机制隔离原样重放的历史会话；CRC 不提供身份认证，没有密钥或 MAC 时不能阻止修改字段并重新计算 CRC 的主动伪造。随机挑战碰撞概率非零。

## 测试口径

每组先下行再上行，不是同时双向持续负载。两方向使用相同整包尺寸和固定窗口。数据丢包率为未收到或未通过校验的数据发送次数 / 实际数据发送次数（含重传）；重传、重复、乱序、ACK 超时和最终完成状态分别记录。未发送的计划包不计入丢包率。

ACK 到达后在首个分片提交前取消的包不计发送次数；已提交部分字节后取消的重传计一次发送尝试，其未完整接收也计入上述丢包率，另记录 `cancelled_partial_frames` 和已提交字节数。这类主动取消的是已确认数据的重复副本，不代表业务数据丢失，不能将其与空口自然丢包混为一谈。

输出表横轴包大小、纵轴窗口大小，每格为「下行 kB/s / 上行 kB/s / 下行丢包率 / 上行丢包率」。失败组必须标记，不能作为稳定速率。

## 测速应用载荷

独立的 `ble-bench-payload` crate 定义应用字段，不扩充链路类型。DATA 首字节 0 表示测试数据，后续字节才计入有效吞吐；首字节 1 表示上行启动，后接 count:u32、payload_length:u16、window:u16。启动命令占该方向一个 DATA ID，重复执行受到序号和结果缓存保护。

诊断 ACK 可附带应用元数据：单字节 2 查询快照；33 字节响应以 3 表示下行统计、4 表示上行结束，后接 8 个 u32 计数。普通空载荷 ACK 不触发应答。快照查询可重复，返回当前或缓存计数，不占数据 ID，也不跨过数据缺口。只有显式查询会回复统计，不能对所有 ACK 互相应答。

整包 N 字节包含 31 字节链路开销和 1 字节测试标识，有效数据为 N−32 字节。历史 v3 为 N−31 字节，且采用整窗调度；对照不能归因于语言单一因素。
